# api.mixroute.ai 验证简报

**验证日期**：2026-05-06（§6.1 补充为 2026-05-07）  
**技术版**：[newapi-mixroute-validation-2026-05-06.md](newapi-mixroute-validation-2026-05-06.md)  
**说明**：下列结论来自在指定云主机（`ubuntu@54.238.141.156`）上、使用仓库标准脚本对网关 `https://api.mixroute.ai/v1` 的拨测；反映当时网络、密钥与时段下的观测结果，**不等同于**供应商长期服务等级承诺（SLA）。与 [2026-04-09 简报](newapi-mixroute-validation-executive-brief-2026-04-09.md) 并列阅读时，请注意**本节是否重跑了与 4 月完全相同的压力档**。

## 一、我们验证了什么

1. **连通性**：四种模型在「OpenAI 兼容对话」与「Anthropic Messages」两种常见对接方式下是否可用。  
2. **大提示词 + 长回答**（脚本 `heavy`、峰值并发 **16**，与 4 月技术报告 §5.1.1 **同参**）：观察整段墙钟内的平均请求节奏（技术版字段 `approx_throughput_rpm`），并据此给出 **TPM 粗算**（估算方式与局限同 4 月简报）。  
3. **短对话 + 高并行**（脚本 `minimal`、固定 **256** 路并发、最多 **4096** 次成功）：观察另一类负载下的平均吞吐；该档与 `heavy` **不可直接对比业务「能扛多少字」**。  
4. **未重跑**：4 月简报中用于给出 **~105.5 RPM / ~116 万 TPM** 的 **heavy 32→512** 高并发探针，**本次未执行**（费用与耗时极高）；若对外承诺需与该档对齐，请以 [2026-04-09 技术版](newapi-mixroute-validation-2026-04-09.md) §5.1.2 或按需补跑为准。

## 三、性能与容量（RPM 与 TPM 估算）

### 3.1 大负载（heavy，gemini-3-flash-preview，峰值并发 16）

与 4 月技术报告 **§5.1.1 同参**（约 **1 万** 脚本侧输入 token 目标 + **最多 1000** 输出 token；最高并行 **16**）：**31** 次请求全部成功，总墙钟约 **50.65 秒**，**未观察到 429**。

**每分钟请求数（RPM）**（成功次数 ÷ 总秒数 × 60）：

**RPM** = 31 ÷ 50.6499 × 60 ≈ **36.7**（次/分钟，与技术版 `approx_throughput_rpm=36.72` 一致）。

**每分钟 token 量（TPM，粗算）**：仍按「单次约 **10 000 + 1 000 = 11 000** token」的**假设**推算（与 4 月简报口径一致，便于对照；真实计费以网关与账单为准）：

**TPM（估算）** ≈ 36.72 × 11 000 ≈ **403 920**（约 **40.4 万 TPM**）。

**与 4 月同参对照**：4 月技术版同一场景约为 **21.6 次/分钟**；本次 **36.7 次/分钟** 更高，属**时段与排队差异**，**不宜**据此断言「容量永久提升」或「永久下降」。

### 3.2 高并行短对话（minimal，256 并发，4096 次成功）

另一脚本形态下，**4096** 次短请求全部成功，整段墙钟约 **141.8 秒**，技术版 `approx_throughput_rpm` ≈ **1733**（次/分钟量级）。

**业务表述**：说明在**极短用户消息、固定 256 并行、该时段与密钥**条件下，平均「完成请求」的节奏可以很高；**不能**与上一小节的大负载 RPM/TPM **混为一谈**，也不宜用 11 000 token/次的假设去乘算 TPM。

### 3.3 关于 4 月简报中的「~105.5 RPM / ~116 万 TPM」

该数字来自 **heavy、峰值 512 并行** 的一次长测（见 [2026-04-09 简报 §3](newapi-mixroute-validation-executive-brief-2026-04-09.md)）。**本次未重跑该档**；若对外材料仍引用「约 105 次/分钟、约 116 万 TPM」，请标注来源为 **2026-04-09**，或安排补测后更新。

### 3.4 补充（2026-05-07）：双进程极限加压下的「窗口发起 RPM」观测

在技术版 [§6.1](newapi-mixroute-validation-2026-05-06.md#61-补充2026-05-07双进程-overlap-加压--首次失败锚定的窗口-rpm含服务端错误) 的一次补充实验中，同一主机上 **并行两个** `overlap` 探针进程（短 prompt、`gemini-3-flash-preview`，单进程最多 **2048** 次发起、并发爬坡至 **12000** 上限）。**先出现失败**的一路（进程 A）在 summary 中的 **`window_60s_requests_started`（60 秒窗口内发起数）** 为 **1380**。若以同一锚点对 **`rpm_dual_A.out` / `rpm_dual_B.out`** 合并统计（两路 `ok`/`fail` 行的 `t_start` 落在锚点前 60 秒内），则一路约 **1380**、另一路约 **1385**，**合计约 2765**（同一分钟内「双进程叠加」的发起量级）。

**TPM（粗算，非账单）**：探针未逐条记录 `usage`。在「单次约 **40** token（**input≈30 + output≈10**，含网关模板等假设）」的中位假设下：**2765 × 40 ≈ 11.1 万 TPM**；若仅按用户正文 tiktoken + 极短输出（约 **8** token/次）则约 **2.2 万 TPM**；若与 sxwl minute 报告并列采用 **~200 token/次** 的宽松口径则约 **55 万 TPM**。详见技术版 §6.1 表格。

失败形态主要为 **连接错误与超时**，**不是** HTTP **429**；上述数字表示该次加压下的观测值，**不宜**直接说成供应商公布的「RPM/TPM 上限」，也不宜与 §3.1 / §3.2 的整段墙钟平均吞吐混为一谈。

## 四、响应时间（快慢大致是什么水平）

### 4.1 大负载（heavy，峰值并发 16）

| 指标     | 数值（秒） | 通俗理解       |
| -------- | ---------- | -------------- |
| 最快     | 约 7.3     | 部分请求较快   |
| 一半请求 | 约 8.9     | 半数不高于此   |
| 最慢     | 约 14.9    | 本次长尾相对收敛 |

### 4.2 短对话高并行（minimal，256 并发）

| 指标     | 数值（秒） | 通俗理解                 |
| -------- | ---------- | ------------------------ |
| 最快     | 约 1.3     | 短请求整体更快           |
| 一半请求 | 约 3.6     | 半数不高于此             |
| 最慢     | 约 47.9    | 仍存在排队带来的慢请求 |

**业务表述**：负载形态不同，延迟数字**不可横向替代**「用户体感」；大负载与小请求应分开解读。

## 五、用量快照（单次短对话、max_tokens=512）

四模型各 **1** 次、同一中文问候下，网关返回的 `usage.total_tokens` 大致为 **68～518**（Gemini 明显高于 Claude，与统计口径有关，**不等于**可见正文长度）。对外沟通成本时，仍以**账单计量**为准。

## 六、风险与后续建议

1. **密钥安全**：若 Key 曾出现在聊天或非私密渠道，**尽快在 NewAPI 后台轮换**。  
2. **指标口径**：本简报的 RPM/TPM（§3.1）来自 `rpm_until_limit` 的整段墙钟平均；技术版另有 `rpm_minute_window_probe` 的 **60 秒窗口「发起数」** 等定义，二者**不可混用**。  
3. **未重跑项**：heavy **32→512** 未在本次重复；**overlap** 双进程加压已于技术版 §6.1（2026-05-07）补充；对外承诺「极限吞吐」前建议按需补测并更新简报日期。  
4. **环境单一**：验证在固定云主机上完成，生产地域与网络不同，表现可能不同。
